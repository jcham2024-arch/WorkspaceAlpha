docs/contracts/decisions/Q1-rpo-rto.md::decision

Decision

Decision

Option A (Sync on every write) for the primary SQLite store.

Rationale: - Audit trail is immutable by design — any loss is unacceptable - Write volume is low (≈10-50 records/session), so latency cost is negligible - WAL mode + PRAGMA synchronous=FULL provides crash consistency without application complexity - JSONL secondary export provides additional durability layer

Key Observations

docs/contracts/decisions/Q2-sqlite-sync.md::decision

Decision

Decision

Use PRAGMA synchronous=FULL for the audit database.

Rationale: - p99 write latency (8.2ms) < 10ms target with 20% margin - Zero data loss on crash/power loss — required for immutable audit trail - Read performance unaffected - Simpler than application-level durability logic

docs/contracts/decisions/Q4-skill-categorization-stability.md::rationale

Rationale

Rationale

The categorization schema is a contract between the master library and the provisioning pipeline. Downstream consumers (provisioning, skill picker, index generator, audit tool) read the CSV by column name. Industry practice for such contracts:

1. Additive changes are safe — new enum values don't break readers 2. Renames/removals are breaking — readers reference values by string 3. Versioning signals intent — major version = breaking change, minor = additive 4. Migration tooling required for breaking changes — not optional

This mirrors semantic versioning for data contracts (cf. Protobuf, Avro, JSON Schema evolution rules).

Industry baselines for static site generators and documentation pipelines:

| Approach | Examples | Trade-off | |----------|----------|-----------| | Full rebuild | Sphinx, MkDocs (default), Hugo, Jekyll | Simple, correct, fast enough for small corpora | | Incremental | VitePress, Next.js, Astro | Complex cache invalidation, risk of stale output | | Hybrid | MkDocs --dirtyreload, Sphinx -j auto | Opt-in, development only |

docs/contracts/decisions/Q6-profile-provisioning.md::rationale

Rationale

Rationale

Industry patterns for capability provisioning:

| Approach | Examples | Trade-off | |----------|----------|-----------| | Static manifest | Cargo.toml, package.json, go.mod, Python requirements.txt | Explicit, auditable, reproducible, reviewable | | Dynamic query | npm workspaces, Bazel labels, Nix flakes | Flexible, but opaque; "what skills does this profile have?" requires running code | | Hybrid | Poetry groups, Cargo features | Best of both: static manifest with optional dynamic composition |

Static manifests win for auditability and reproducibility. A human (or CI) can read .agent/profiles/conceptualizer.md and know exactly which skills are provisioned without executing code. This is critical for: - Security review: "Does this profile have the shell skill?" - Reproducibility: Same commit → same active skill set - Debugging: "Why does this profile have skill X?" → check frontmatter, not query logic

The dynamic fallback (--dynamic) supports development exploration (e.g., "give me all task_type=planning skills") but does not replace the committed manifest.

Provenance

Provenance

The dump aggregates 13 buckets (see .archive/Agentsandskills/agent.md and .archive/Agentsandskills/AgentSkills/DATABASE.md for the full inventory, which is stale — counts disagree across files, by-source/ lists only 6 of 13 buckets, harness-skills-names.txt lists 28 of 60 installed). Every SKILL.md keeps original frontmatter; nothing here is rewritten. (The dump's OVERLAPS/INSTALLATION/DATABASE files are no longer present post-clear; treat as historical notes.)

Why is the dump not indexed?

- 136M of 150M is dump/agentic-awesome-skills (2,947 skills), with uniform frontmatter but no per-skill quality signal. Auto-ingesting it would swamp the router (3,509 nodes, most low-signal) and break the 150-line AGENTS.md token budget. - Bulk install is prohibited by OVERLAPS.md / INSTALLATION.md. Install one skill at a time, diff it first. - Trust spread: security-offensive skills (active-directory-attacks, windows-privilege-escalation, apk-reverse, XSS, api-fuzzing) carry risk: offensive/critical and impose their own confirmation gates. Never auto-install security skills, x402 (USDC payments, installed copy included), or any skill with executable scripts/ without review — scripts ship unsigned. - License field is inconsistent (MIT in some, absent in others); external GitHub URL dependencies exist (e.g. aws-skills router).

Integrity findings

- 3 installed skills are broken at source (SKILL.md = "404: Not Found" in both .harness/skills and dump/): caveman, karpathy-coder, llm-cost-optimizer. Excluded from the workspace copy (57, not 60). - caveman, karpathy-coder, llm-cost-optimizer names collide with healthy skills elsewhere (dump/ponytail has a real caveman pack; andrej-karpathy is the healthy Karpathy skill) — check OVERLAPS.md before installing any dump copy. - agent.md count claims (60 vs 28 vs 27 installed, 3,405 vs 3,413 vs 3,509 total, 14 sources for 13 buckets) are mutually inconsistent. Treat DATABASE.md/INDEX.csv as approximate; verify on disk.

docs/specs/audit-persistence-spec.md::functional-requirements

Functional Requirements

Functional Requirements

1. Immutable Audit Trail: Once written, audit records cannot be modified or deleted 2. Queryable: Support filtering by timestamp, agent, task, outcome, and tags 3. Partitioned: Store by date (YYYY-MM-DD) for efficient time-range queries 4. Compressed: Use efficient binary format for long-term storage 5. Replicable: Support export/import for backup and migration
